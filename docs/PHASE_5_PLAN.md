# Phase 5 plan — Weekly payroll and PDF payslips

The owner approved checkpoint 5a with the amendments below. The accepted baseline is checkpoint 4b with 34 application tables, 49 migrations and 198 passing tests. This plan covers blueprint Sections 9, 10, 12, 14 and 15. Hosting remains local. Payroll policies are decisions for the owner/accountant, and the application must display missing decisions and block approval and payment.

## 1. Checkpoints and blueprint alignment

| Checkpoint | New application tables | Working exit |
| --- | --- | --- |
| **5a — Payroll** | `earning_types`, `deduction_types`, `payroll_periods`, `payroll_lines`, `payroll_items`, `payroll_item_attendance`, `payroll_adjustments`. **7 new, 41 total**. | Configure rules with MFA, open a canonical week, prepare and review drafts, resolve source issues, record adjustments and freeze an approved snapshot. Verify that different rates and corrections reconcile and that approved amounts remain immutable. Report and wait for acceptance. |
| **5b — Payslips and payment** | `payslips`, `payments`. **2 new, 43 total**. Reuse `file_objects` and private storage with a new typed payslip owner. | Issue immutable A4 PDFs, authorize employee downloads, record payment once, publish a new PDF version reflecting payment, and export as administrator. Reuse `audit_log`, the existing session and policy tables, and receipts on the rows that own each operation. The original Phase 1 design's PDF job table, notification table and standalone idempotency table are excluded. The app records payments made outside it. It has no connection to a bank, client system or invoicing database.

Blueprint §9 couples approval with PDF generation. The requested split stages that combined outcome. In 5a an approved snapshot is explicitly labeled as awaiting payslip issuance. In 5b approval starts synchronous issuance after the financial commit and shows the actual issuance result. Already approved 5a lines use the same guarded issuance action. A file failure leaves the approval intact and makes issuance retryable. The completed Phase 5 gate requires a usable private PDF. This sequencing is the only change to when the blueprint's PDF result becomes available.

## 2. Tables and integrity rules

Use UUIDs, real foreign keys with restrictive deletes, explicit actor references, UTC `timestamptz` and Manila calendar `date` where appropriate. Index foreign keys, review queues and bounded employee/period history queries. Mutable rows use optimistic versions. Amounts use finite, bounded PostgreSQL `NUMERIC` and PHP currency checks; time allocations use exact microseconds. Before writing fixed-scale amounts, reject excess precision or apply the selected rule explicitly.

| Table | Proposed columns and database constraints |
| --- | --- |
| `earning_types` | ID, stable code, revision, effective Manila date, name, category (REGULAR, PREMIUM, BONUS, ALLOWANCE, ADJUSTMENT), enabled, validated rule description, actor, reason and timestamp. Unique code/revision and code/effective date. Append a revision to edit or retire. Configure the REGULAR type explicitly. Every other category takes a reviewed manual amount. |
| `deduction_types` | Same revision/effective-date structure. Category (STATUTORY, WITHHOLDING, CONTRIBUTION, LOAN, OTHER), validated rule description and applicability. Empty at setup. Exactly referenced revision is retained on an item. |

Unique boundaries and GiST exclusion over `daterange(start_date,end_date_exclusive,'[)')`; normal periods are seven days aligned to their validated weekday. Successors use the existing period ID. Approval freezes the bounds, payday and original roster/manifest. |
| `payroll_lines` | ID, period and employee FKs, positive revision, optional unpaid predecessor, state, PHP currency, gross/deductions/net, draft issues and source digest, frozen snapshot and digest, actors and timestamps, version and receipts. Unique period/employee/revision and a composite same-period/employee predecessor FK. Partial unique indexes enforce one draft and one approved or paid obligation per period and employee, and one replacement per predecessor. Gross and deductions are nonnegative and net equals gross minus deductions. Negative drafts block approval. |
| `payroll_items` | ID, line and employee, sequence, kind EARNING or DEDUCTION, matching typed revision FK, description, rate FK where applicable, applied PAY policy FK, service date, exact quantity/rate inputs, final amount and calculation snapshot. Unique line/sequence. Composite FKs enforce line/employee and rate/employee ownership. Regular items require an eligible rate. The database validates type, dates and rule snapshot against the selected line inputs. |
| `payroll_item_attendance` | Item, line, employee, shift, service date, exact UTC interval bounds, allocated seconds, original duty date, captured shift version and review evidence, and break allocation snapshot. PK over item, shift and service date. Composite FKs enforce same item/line/employee and shift/employee. Finalization verifies eligibility and interval bounds and rejects overlapping attendance already paid in a different period. Manual items link to their reviewed adjustment. |
| `payroll_adjustments` | ID, line/employee/period, adjustment kind, optional related correction, original line or shift version, actor, reason, evidence, before/after values, timestamp, operation key and canonical fingerprint. Append-only. Use composite ownership FKs, unique receipts, one review per shift version and one posting per reviewed paid correction. |
| `payslips` (5b) | ID, line FK, positive version, random unique external reference, file FK UQ, issued-at/by, immutable line digest, event kind APPROVAL or PAYMENT, payment FK when applicable, template/branding digest and generation receipt. | `payments` (5b) | ID, line FK UQ, real payment date, immutable method code and normalized reference, exact amount, reference-policy FK, recorded-by/at, reason, operation key and fingerprint. A guarded transaction verifies amount equals approved net and binds the payment to the state transition. Append-only. |

The schema uses existing `policy_versions` for immutable PAY revisions and `company_settings.pay_policy_id` as the current configuration pointer. Add a typed effective Manila date and reason for Phase 5 PAY versions, with a unique PAY effective date and database-enforced kind/shape checks. Preserve legacy PAY records and their rate FKs as historical evidence. Legacy seed values such as Monday and HALF_UP are **UNCONFIGURED** for Phase 5, even if their keys exist. Protect PAY creation and the company pointer against direct runtime writes that could bypass the validator. Publish a complete immutable version with the effective catalog/calendar selection, then apply it from its declared date. Existing rate `pay_policy_id` records the context when the rate was written. Calculation resolves the PAY version effective on each service date separately and freezes both references.

## 3. Policy decisions and proposed assumptions entry

These approved constraints supersede the earlier provisional payroll defaults. See [ASSUMPTIONS.md](ASSUMPTIONS.md).

| --- | --- |
| Employee basis and paid day | **UNCONFIGURED**. Select DAILY or HOURLY through the applicable rate history, with amount and effective dates. Define payable-day qualification, expected time, and whether multiple shifts combine toward one day. A missing rate, schedule or applicable decision blocks the affected calculation. A confirmed not-applicable choice may close a rule that does not apply to that basis. |
| Payable source, breaks and overnight allocation | **UNCONFIGURED**. Proposed source is closed, eligible, administrator-approved attendance with explicit `approved_payable_seconds`. Owner confirms use of captured MEAL/SHORT treatment or requires attendance review under corrected treatment. Choose the overnight allocation rule before approval. Proposed split by Manila service date at midnight, preserving the authorized duty date and exact original timestamps. |
| Partial days, thresholds, lateness | **UNCONFIGURED**. Bounded typed choices such as proportional daily pay, explicit threshold treatment or manual review. Minimum pay and lateness each require an explicit rule or confirmed no adjustment. No automatic unpaid time from lateness, login, a task gap or a missing punch. |
| Time and monetary rounding | **UNCONFIGURED**. Configure each independently, including explicit NONE. Specify unit, application stage, direction and tie rule for supported modes. Preserve exact recorded attendance and show the effect on calculated payable quantities separately. Monetary rounding is explicit at item finalization and totals sum posted items. |
| Overtime, rest days, holidays and premiums | **UNCONFIGURED**. Explicitly permit manual entries or select NONE for each classification. An administrator enters each amount with recent MFA, reason and evidence. Display WORK holiday dates as context. |
| Allowances and bonuses | **UNCONFIGURED**. Configure eligible types and rules or confirm none. Fixed or explicitly reviewed per-line amounts carry an actor, evidence and reason. |
| Contributions, withholding, loans and deductions | **UNCONFIGURED**. Select catalog treatment or explicitly confirm none. Catalog entries require an employee or exact designation, effective date and reason. Amount rules are FIXED or MANUAL. Seed the catalog empty. |
| Weekly cutoff and payday | **UNCONFIGURED**. Choose the ISO weekday defining the Manila week start and the payday rule relative to period end. Midnight boundaries are start-inclusive and end-exclusive. Once any payroll period exists, reject a different weekday. |
| Payment and reference | **UNCONFIGURED**. Choose permitted methods, reference validation/canonicalization, allowed actual payment dates and zero-net handling. Use bounded reference templates rather than arbitrary regexes. Reject future actual dates. Reference normalization is stable for each method; changing its meaning requires a new code. Zero requires explicit accountant review as no disbursement due and creates no payment. A negative net blocks approval and payment. |

Saving incomplete decisions can support review, with a clear list of missing settings. Only an MFA administrator with recent verification, a mandatory reason and the expected current revision can publish an applicable setting. The approval and payment transactions each check readiness. Payment uses the applicable configured payment rules and verifies compatibility with the frozen line. Incomplete or incompatible changes block recording until resolved. Any change in pay settings is auditable and effective-dated. It never rewrites finalized financial content. Actual classification, legal treatment and financial choices remain for the owner/accountant to supply.

## 4. Drafts, approval and corrections

1. **Prepare.** An MFA administrator opens a configured week and previews an explicit employee roster. Use employment dates and stored attendance/correction evidence, so disabling an account does not drop earned history. Reconcile due attendance with the existing bounded logic. Recompute only eligible drafts and retain the review trail. Collect blockers for open or unapproved shifts, unresolved flags, pending shift or missing-punch requests even when they have no shift row, missing rates/schedules/rules, and negative net. Missing expected punches surface as an issue based on schedule/duty evidence. No time or pay is fabricated for an empty day.
2. **Allocate.** Start with the exact approved total per shift. Split at configured Manila service-date/cutoff boundaries and use the rate and PAY revision effective for each date. If approved seconds match the eligible elapsed intervals, use the actual closed break intervals for exact attribution. If an approved override cannot be inferred from interval evidence, require explicit, reasoned allocations with recent MFA. Each slice must fit its elapsed source and the slices must sum to the approved total. Never silently prorate an override. Combine multiple same-day shifts before applying an explicit daily rule. Build itemized regular quantities, premiums, allowances, bonuses and deductions. Task time and its gap are excluded from the calculation.
3. **Resolve and review.** A flag remains blocking until the underlying issue is resolved. The 4a flag arrays keep historical flags even after correction. For a corrected missing punch, require the applied immutable correction and a fresh explicit attendance approval. Preserve the old flag as evidence. For flags that require classification, such as non-working day or lateness, require a configured rule and a reasoned, source-version-bound review of that issue. Overtime approval identifies the eligible shifts and exact seconds in the review evidence. A blanket acknowledgment cannot make a missing, open, disputed or unapproved shift eligible. Changes invalidate stale issue resolutions. Reviewers see included/excluded shifts, source versions, dates, rates, rounding effects, gross, deductions and net.
4. **Freeze.** An administrator with recent MFA approves the expected manifest and versions after the trusted clock passes the period's exclusive cutoff. Under lock, validate the complete reviewed roster, cutoff, current source eligibility, allocations, policies, catalog revisions, rate intervals, required provenance, item sums and readiness. A changed or newly relevant source, including a new missing-punch request, forces a fresh preview. Freeze the period and all selected lines atomically. Snapshots include employee name/ID/position, company identity, bounds/payday, all applied dates, schedule/attendance review evidence, rate and policy contents, item calculations, amounts, rounding and reviewer/approval date. Make the snapshot, source links and finalized items immutable through grants, triggers and guarded commands. A correction that commits afterward leaves the snapshot intact and is surfaced against the historical line via source-version drift and correction evidence.
5. **Correct.** Recalculate drafts from current approved sources and preserve reviewed manual adjustments. Void an unpaid approved line or prepare a replacement within the same period. Approval of the replacement atomically marks its predecessor ADJUSTED and ineligible for payment. For a paid line, record the correction need with reason and evidence and link it to an explicitly reviewed manual adjustment on a later-period line. Preserve the original paid line, payment and PDF. Confirm later-period treatment and authorization with the owner/accountant.

State transitions are `DRAFT → APPROVED → PAID`, plus `APPROVED → VOIDED` or `APPROVED → ADJUSTED` for audited unpaid disposition. Regenerating a draft keeps its identity and review trail. Payment recording, guarded status update and audit commit together in 5b. Approval writes no payment. The same operation key and canonical fingerprint return the prior authorized result. Reusing the key with a changed payload conflicts.

For arithmetic, reuse the exact-decimal parser/formatter where suitable, adding an exact path for fractional seconds and quotients. Existing money helpers with implicit HALF_UP or integer-second input are unsuitable for calculation without an explicit selected rule. Use scaled integers or exact numerator/denominator arithmetic to retain microseconds and rates through division; compare remainders exactly at rounding ties. Serialize money as decimal strings, including API, JSON snapshots and export inputs. For explicit monetary NONE, a non-cent-exact item is a visible blocker until the owner selects a rule or reviews a representable item. Never let a PostgreSQL scale conversion or display formatter choose an unconfigured rounding rule.

## 5. Locking and authorization

Use the existing policy advisory lock (shared for work, exclusive for policy publication), sorted affected user rows including the actor, authenticated session and applicable duty rows, project/task/assignment parents if needed by an existing correction, shifts, breaks, timers and attendance adjustments. **Payroll locks follow these sources** in period ID, employee/line revision, item/link/adjustment, then payslip/payment/file order. Pure payment and issuance writes may skip attendance locks and operate on the frozen snapshot. For a new period use the unique/exclusion constraints plus conflict handling; avoid grabbing a period lock before reaching back for employee/time locks. No payroll-specific global gate. Sort and bound multi-row work, re-read roster and source versions after locks, revalidate MFA, and handle expected-version or serialization conflicts explicitly. A race with a punch correction must either freeze the new reviewed evidence after fresh preview or leave a frozen snapshot followed by a controlled correction.

Every new table has RLS. Runtime receives narrow SELECT grants or guarded projections and guarded mutation functions only. Definer functions use a fixed search path, live database-derived identity and MFA checks, and explicit scope/version predicates. Require recent MFA for approval, source or financial adjustments, voids, successor decisions and payment recording. Derive regular pay from verified source quantities and rates. Guarded writes reject arbitrary totals, forged source proofs and manual item amounts without a reviewed adjustment. The auth role has no new table access. Deny direct catalog/policy writes and finalized row updates or deletes, including attempts through older settings or file functions.

Administrators with MFA can administer payroll without DUTY. Employees with a valid ACCOUNT session can see only their own finalized lines and payslips, including off duty, and continue to see their own rate history. DUTY and SETUP alone grant no payroll access. Employee projections omit raw snapshot JSON, draft content, internal audit/reviewer notes, peer rates, payment references and storage keys. Do not use an employee ID from one session with privileges from another. Protect SSR, RSC, route handlers, lists/counts/exports and direct SQL; return the same 404 for missing and foreign IDs for valid callers. Apply CSRF, origin checks and private/no-store responses. Recheck access between download/export chunks and abort on disablement or session loss. Use responsive pages with actual statuses and actionable issue messages.

## 6. Payslip issuance and exports in 5b

- Render an A4 PDF from the frozen snapshot and the relevant immutable approval or payment event. Include Libetario Digital Marketing Services, configured local logo if available, employee name/ID/position, unique payslip reference, period and rate basis (show each if mixed), days/hours, basic pay, premiums/overtime, bonuses/allowances, itemized deductions, gross/net, approval date and payment status/date. Use repeatable headings/page breaks for long item lists. An absent or invalid logo falls back to the company name and a visible admin configuration message. No remote fonts or network requests. Review the already lockfile-pinned `pdf-lib@1.17.1` for generation, including dependency audit and local font coverage for employee names and PHP display. Pin any added font support or export dependency and record its license.
- Extend `file_objects` with a payslip purpose and allow NULL project only for that purpose. Require exactly one typed owner across project, task, submission and payslip links. Guard immutable file identity, size and SHA-256; derive payslip access only from its linked finalized line. Keep payroll objects out of work file lists, locators and cleanup paths unless the specific operator cleanup is for verified orphaned payroll bytes. A payslip reference is random, opaque and separate from the random storage key. The HTTP path uses an authorized reference and never exposes the storage key or a public file URL.
- In the authenticated request, render bounded bytes to exclusive private staging, validate and hash, promote via the existing path-safe storage and publish the typed file and version together in a short database transaction. Recheck live authority and the line/event version at publication. A competing retry reuses the published version; it cannot replace its bytes. On failed publication, clean only the known unreferenced candidate. For a crash or uncertain commit outcome, check committed ownership before a bounded operator cleanup. A durable file promotion and DB commit are separate effects. A prior PDF stays accessible if a later issue fails. The payment event can be retried for PDF issuance without recording payment again. The original Approved PDF remains unchanged when the Paid version becomes available.
- Employees list and download individual finalized PDFs. Verify file size and SHA-256 before serving, use attachment disposition, `nosniff` and `no-store`, and apply the existing protected-download behavior for HEAD/range/conditional requests. Admin batch export uses bounded date/employee filters, authorization checks for every PDF and archive chunk, and preflights availability and size. Propose up to 100 PDFs or 100 MiB per archive, with explicit errors for missing/corrupt files or excess size. Admin payroll CSV reuses the formula-safe encoder and bounded streaming; include separate approval/payment status, verify scope and fail on overflow rather than truncate. Back up the private bytes with the database.

## 8. Windows test command and approval gates

Use `pnpm test:all:win` with the README instructions. Copy source and test files into a temporary checkout. Provision and migrate fresh disposable PostgreSQL clusters and databases with restricted roles, random loopback ports, private roots and separate keyrings for each suite. Load fake seeds and suite-specific fixtures. The test environment is limited to that run so clock overrides, lockouts, keys and files from an interrupted invocation cannot affect the next one.

Start Next with webpack on the run's loopback port and wait for HTTP readiness. Run the same test entry points as `pnpm test` and `pnpm test:http` in sequence. A Windows Job owns the process tree and stops it if the runner is terminated. Normal exit also removes the run's temporary data. Verify consecutive passes and a fresh pass after interrupting a run that has changed test state.

Deliver 5a with its report and wait for owner acceptance. Actual payroll values remain unconfigured until the owner/accountant supplies them.
