# Phase 2b security, deployment and backup notes

For the current release, use the [release security checklist](RELEASE_SECURITY.md) and [operator runbook](RELEASE_RUNBOOK.md). This document records the earlier 2b checkpoint.

## Trust boundaries

The application never imports migration credentials. `DATABASE_URL` must authenticate as `libetario_runtime`. That role cannot bypass RLS, own the tables, set the authentication role, read password hashes, read session/reset-token hashes, read throttle rows, delete history, or modify audit/security events. Employee-owned SELECT policies derive the current identity from an active, unexpired, non-revoked session whose authorization version still matches its enabled account. The context is an unguessable session-token hash, not a user ID or role supplied in a request. Transaction-local context is discarded on pooled-connection return.

`AUTH_DATABASE_URL` uses the distinct `libetario_auth` authority. This role has only the credential columns and authentication/session/throttle/reset operations needed to authenticate users. It cannot read profiles, rates, schedules or audit records and cannot assume the runtime role. It is deliberately trusted to verify passwords and issue sessions; compromise of authentication authority remains a credential-boundary compromise. Database clients and auth services are server-only through the `server-only` database module. PostgreSQL superuser/table-owner credentials are confined to setup, migrations, development seed and test fixtures.

RLS is enabled on all seventeen application tables. The runtime role can read only safe MFA metadata under own/admin policies; it has no PIN/recovery-table access, enrollment ciphertext/nonce/tag access or MFA/session-claim mutation. Some sensitive tables have no runtime grants at all. The runtime role is not the owner; SECURITY DEFINER identity/audit/reset functions have fixed search paths, revoked PUBLIC execution and explicit grants. Owner functions can inspect auth state without recursive RLS policies. Do not make app roles table owners, grant BYPASSRLS, grant role membership between them, or expose database ports publicly. RLS is defense in depth alongside explicit service guards, schema validation, strict role/ownership routing, and minimal projections.

All state-changing HTTP endpoints require the exact configured Origin, reject `Sec-Fetch-Site: cross-site`, and verify a CSRF token. Anonymous login/reset forms use a signed double-submit cookie; authenticated forms use a session-bound HMAC token. Cookies are HttpOnly and SameSite=Lax; Secure is required for HTTPS production. Responses are private/no-store. Per-request nonce CSP disallows arbitrary inline scripts, alongside frame denial, nosniff, referrer restrictions and permissions policy. Development requires `unsafe-eval`; production does not. Styles allow inline style attributes for framework compatibility.

Passwords use Argon2id (19 MiB memory, two iterations, parallelism one). Unknown identifiers still perform a dummy password verification to reduce obvious account enumeration. Account keys unify email/username; network keys are keyed hashes. Counter updates and password verification are serialized with transaction advisory locks. Password changes, resets and disabling invalidate persisted sessions immediately. Reset tokens and session tokens have 256 bits of randomness and only SHA-256 hashes are stored. Reset consumption and revocation are transactional. Expiry is enforced by PostgreSQL timestamps, not a client clock, and recorded when encountered.

Audit events retain old/new values and reasons. Password hashes, raw passwords, session tokens, reset tokens, PINs and TOTP secrets must never be placed in an audit payload, URL, console output, telemetry or error response. Tables deny UPDATE/DELETE/TRUNCATE to app roles and have defensive immutability triggers. Administrative writes create audit events in the same transaction. Migration/DBA access remains a separate privileged operational boundary.

## MFA and recovery

Administrator password login produces a restricted SETUP session; ordinary RLS identity is empty until confirmed TOTP yields a new ACCOUNT session. A database trigger also prevents administrator ACCOUNT creation without a confirmed user-bound enrollment and MFA attestation. No old session is grandfathered. Employees can retain account-only access to their own records; MFA is mandatory for duty. SETUP is five minutes absolutely, is bound to the user/session/current policy, and rotates on completion. Policy changes revoke unfinished setup sessions. DUTY is a separate scope/cookie and never satisfies ordinary ACCOUNT identity.

TOTP uses OTPAuth's RFC 6238 SHA1/6-digit/30-second implementation and ±1-step verification. Row locks plus strictly increasing last_accepted_step prevent concurrent or subsequent reuse. First confirmation consumes its step. Persisted per-account, network and session attempt counters enforce independent factor lockouts; new setup sessions cannot clear existing locks. PINs and 160-bit recovery secrets use Argon2id; raw values are never retrievable after their once-only response. Code batches are revoked on regeneration/reset and individual consumption is transactional.

Each enrollment has a fresh 256-bit secret encrypted using AES-256-GCM, 12-byte random nonce and 16-byte tag. Associated data binds format, user, enrollment, generation, key ID and TOTP parameters. Key IDs enable rotation; keys reside only in the environment keyring, independently of SESSION_SECRET/database credentials. Missing keys, invalid configuration or tag failure deny verification. The local one-time QR response is private/no-store; its plaintext/URI/image is not persisted, audited or sent to an external QR provider. Secret buffers are cleared after use where supported; JavaScript strings/third-party library buffers remain process-memory data, so server-memory compromise is outside encrypted-at-rest protection.

Password plus an unused recovery code revokes the old enrollment/codes, bumps account authorization_version, revokes all sessions and outstanding reset capabilities, and grants enrollment-only SETUP. It cannot access records or administrator tools until a new generation is confirmed. Assisted reset requires a different full administrator with recent TOTP, separate identity-verification note/reason and a single-use hashed 15-minute reset token. The target still proves password and enrolls anew. Password changes/resets revoke sessions and pending reset tokens without removing MFA requirements.

The last-administrator CLI is server/migration-owner only; request code does not import it and cannot execute the underlying owner-only function. It requires exact typed confirmation and note/reason, audits OS operator/source/target, and refuses production/remote/unrecognized targets without --allow-production. Application-role credentials remain forbidden even with that flag. It does not change passwords, roles or account enabled status. Terminal output includes only the intended one-time private reset token, never encryption keys or authenticator secrets. Do not redirect/capture operator reset output. Local second-admin seeding is explicit, refuses production and requires independent password change/MFA onboarding. See README for commands.

## Duty grant and scope boundary

Duty mutations derive the administrator from the validated database session in fixed-search-path SECURITY DEFINER functions; no supplied actor or direct runtime write is accepted. Unique employee/date grants and real composite FKs bind duty sessions/challenges to the same employee. Function checks require 1–100 unique selected employees, active employment for activation, explicit valid window/policy and a non-empty reason. Identical active snapshots remain no-ops even after work policy changes; revoked grants require reasoned regrant. Revoke/regrant increment authorization_version, invalidate credentials and audit prior/current grant metadata transactionally, retaining history. Disabled employees' grants may still be revoked.

private.duty_context() checks DUTY scope, active account/employment, account version, exact grant/version/state/window, original first-authentication date/version, confirmed enrollment/generation, current SECURITY policy and current PIN version when required. Runtime can read own permitted duty metadata but cannot update grants, inspect challenges, call the auth-only locking/first-authentication helpers or bypass the public duty guard through its owner-only base function. requireDuty() is shared by the HTTP endpoint and page. ACCOUNT/SETUP cannot satisfy it. Login creates no attendance or pay.

Initial duty login uses fresh password -> optional current PIN -> current TOTP. Five-minute challenges bind session/user/grant/policy/enrollment/PIN versions; PIN rotates bearer/CSRF without extending expiry. Foreign bindings are rejected before touching a victim's account throttle. Global accepted TOTP counters are shared across enrollment/account/duty/reauthentication purposes. Final issuance rechecks the live binding and trusted time under policy/user/grant/enrollment locks before consuming the challenge and issuing scope. Password/factor failures retain persistent counters. SECURITY switches serialize against issuance and revoke both incomplete challenges and DUTY access; PIN and account/factor/employment changes invalidate affected credentials.

ACCOUNT and DUTY cookies are separate. Initial duty completion rotates ACCOUNT and issues DUTY; same-grant MFA reauthentication rotates DUTY only. Server duty limits are 30-minute idle, min(valid_until, issuance + configured maximum twelve hours) absolute. The duty cookie may outlive that server session only to bind same-grant MFA until valid_until. Expired or SECURITY/PIN-invalidated handles grant no protected data; current TOTP/PIN/policy are re-proved. Logout, duty version changes, disabling, employment invalidation, account resets or enrollment generation changes cannot revive old handles. Restore operations must revoke all such handles explicitly, including expired records.

Default overnight is off; explicit permitted carry is bounded by WORK's 1–8-hour ceiling and a saved grant window. No next-date activation or new backdated start is implicit. A valid overnight continuation stays on its original date/version; policy edits do not silently stretch its snapshot. UTC connection options prevent local server timezone output from being misinterpreted by the Prisma adapter. Only local test-owner fixtures may replace the private trusted clock function, restoring it in finally; request handlers never expose a clock override.

## Configuration and future hosting

Hosting is local only until the owner selects a target. Production configuration comes from environment variables documented in `.env.example`; do not embed secrets or provider URLs into source. Use a supported PostgreSQL service with `btree_gist` support, encrypted connections, isolated development/staging/production databases, a private connection path, and provider-approved TLS verification. Never use `rejectUnauthorized:false`.

On a fresh provider, the DBA must provision `libetario_runtime` and `libetario_auth` as LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOBYPASSRLS roles, with separately generated strong passwords provided through the secret manager. A distinct migration principal owns application objects and can install the trusted `btree_gist` extension. No role membership is granted to app principals. Create an empty standalone database, revoke PUBLIC schema CREATE and database CONNECT, explicitly grant CONNECT to the app roles, and run `prisma migrate deploy` as the migration principal. Migrations contain permissions but no passwords. Verify the restricted-role test suite on isolated staging before release. Never run `prisma db push` as a replacement for the reviewed SQL migrations: Prisma cannot model all RLS, check, exclusion or trigger rules.

Keep `APP_ORIGIN` as a single canonical HTTPS origin. Serve Next behind a configured HTTPS reverse proxy. Bind Next and PostgreSQL to private/loopback interfaces unless deployment explicitly requires otherwise. Set `TRUST_PROXY=true` only where a trusted proxy strips and sets client forwarding headers; keep it false for local access. False intentionally uses a shared network bucket, which may lock out multiple local users after failures. Session/throttle lifetimes are versioned in Settings, with the defaults in ASSUMPTIONS.md. Protect the session secret and rotate with a planned session-revocation procedure.

No public registration, employee impersonation, file upload endpoint, payslip endpoint, payment workflow, clock-in, timer or attendance exists. Duty grants/challenges/sessions/revocation and overnight access are implemented through 2b. Upload content/size validation arrives before uploads in Phase 3. Timer/shift transactional constraints arrive in Phase 4. Secure PDFs/financial snapshots arrive in Phase 5. These remain explicit unfinished phase gates.

## Backup and restore plan

Before production release, approve retention, backup frequency, encryption/storage/access, recovery-point and recovery-time objectives with the owner. Use PostgreSQL custom-format `pg_dump` backups of this standalone database and encrypted offsite storage. Provide credentials through a restricted password file/secret environment, not command arguments, committed scripts, or logs. Capture the migration revision, role/grant provisioning, app version, secret-manager version references and the database backup together. Never include plaintext secrets in a backup manifest. Password hashes and employee compensation data inside database backups are sensitive.

Back up the MFA keyring **separately** from the database, encrypted under separate access controls. Keep IDs/keys required by retained backup ciphertext. Total key loss forces every enrolled user to re-enroll using recovery/assistance/operator reset after a new keyring is supplied; a database backup cannot reconstruct lost secrets. README documents add-new-ID, restart, transactional re-encryption and old-key retirement. Rotation preserves replay counters/generations and is audited. Never replace a key value under an existing ID.

Restore into a new isolated database using the migration/restore authority; provision the same application role names first. Restore schema/data/triggers/grants and supply its corresponding keyring, verify all seventeen Phase 2 tables and append-only/RLS controls, run restricted-role and app tests, and invalidate all restored sessions/reset tokens, unfinished auth_challenges and every DUTY reauthentication handle (including previously expired handles) before allowing access. Change database credentials as needed and supply the corresponding environment URLs. A production backup/restore drill, storage provider and operational schedule remain release-phase work; the completed migration replay and cryptographic/rotation tests are not presented as a backup restore rehearsal.

The embedded cluster is local development tooling, not a production backup solution. Do not copy its live data directory as an application-consistent backup. Keep `.local/`, `.env*`, backups and test artifacts outside Git and under the workstation owner's access controls.

## Optional integration path

No existing Libetario client/invoicing database was accessed. A future integration requires explicit owner authorization, a separate read-scoped service/API or outbox contract, documented field mapping and stable external identifiers. Do not share database credentials, copy payroll secrets, or add cross-database foreign keys. Preserve this app's role and employee ownership checks at the integration boundary; integration cannot grant another employee access to compensation or payslips.
