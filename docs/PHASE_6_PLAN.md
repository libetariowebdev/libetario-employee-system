# Phase 6 release and hosting plan

**Approved for 6a with amendments.** Phase 6 covers release verification and operating the existing app. The accepted baseline is checkpoint 5b at `a774520`, with 56 migrations, 43 RLS-enabled application tables and 223 tests. The owner executes the runbook over SSH and records the results. [Blueprint §§13–16](BLUEPRINT.md) · [Phase 5b report](PHASE_5B_REPORT.md)

- **6a** covers the runbook, guarded bootstrap, Linux runner and portability checks, paired backup and restore tooling, templates, staging procedure, UAT and security/privacy checklists, and the 6a report. Windows must pass 223 tests twice, plus replay, typecheck, build and audit.
- **6b** covers production provisioning, restore rehearsal evidence, the 2–3 staff pilot, the go-live decision and the 6b report. It requires separate approval.
- Go-live requires the full 223-test suite on Ubuntu 24.04 with PostgreSQL 18. Use a private repository, read-only deploy key, verified tags and a tracked-secret path check. Backups wait within a configurable window for open shifts to clear. On timeout they skip and alert while the app stays up. A final database lock and recheck guard the stop against concurrent Clock In. Stage can use a separate small VPS. See the runbook for minimum sizing and capacity evidence.

## 1. Hosting assumptions and server layout

- **Topology.** Use a standalone HTTPS app at an owner-confirmed hostname such as `team.example.com`. The company WordPress site adds an ordinary link. WordPress and the app have separate sign-in, cookies, hosting and data. The owner controls DNS, has VPS console or rescue access, and will create a named sudo operator account. I have no server access. The workspace currently has no Git remote configured. The owner will identify a private read-only deploy source or use a checksummed release archive.
- **Sizing.** For 10–20 staff, start with Hostinger KVM 2 or equivalent, with 2 vCPUs, 8 GB RAM and 100 GB disk. This is an estimate for two small environments, builds, private files and backup scratch space. Confirm the actual plan and upload volume, build one release at a time, and measure peak memory, disk growth and the nightly maintenance window in staging. One VPS is a shared failure domain even with separate clusters. Offsite backup and a tested rebuild are required. [Hostinger VPS resource limits](https://www.hostinger.com/support/6976044-parameters-and-limits-of-hosting-plans-in-hostinger/)
- **Versions.** Use Ubuntu Server 24.04 LTS x86-64, Node.js 24 LTS and the repo-pinned pnpm `11.25.0`. Select and record the exact patched Node 24.x release at deployment. Use PostgreSQL 18 from the signed PostgreSQL Apt repository, matching the regression runner's major version, with matching client tools and the `btree_gist` extension. Record the exact Linux versions in staging and use them in production. [Ubuntu 24.04 release notes](https://documentation.ubuntu.com/release-notes/24.04/) · [Node.js release schedule](https://nodejs.org/en/about/previous-releases) · [PostgreSQL Apt repository](https://www.postgresql.org/download/linux/ubuntu/)
- **Layout.** Use versioned, operator-owned releases under `/opt/libetario/<environment>/releases`, a `current` symlink, protected configuration under `/etc/libetario`, and separate private data roots under `/var/lib/libetario`. Each environment runs under its own unprivileged systemd identity. Only its private data and required cache paths are writable to the service. Caddy serves the two HTTPS hostnames and proxies to distinct loopback Next.js ports. PostgreSQL listens on loopback on distinct cluster ports. Private uploads, quarantined files and payslips are outside both the release and web roots, with no static file mapping from Caddy.
- **PostgreSQL roles.** In each cluster create a distinct migration login that owns the standalone database and its application objects. Keep superuser duties with the local PostgreSQL administrator. The app uses exactly `libetario_runtime` and `libetario_auth`, each LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT and NOBYPASSRLS, with no cross-membership. Restrict database CONNECT and schema CREATE, use loopback SCRAM authentication, and document matching database and role rules in `pg_hba.conf`. The same role names are required by the migrations and app, so staging needs a second cluster for independent credentials. No migration or superuser credential enters the web service environment.
- **Edge and host hardening.** Use Caddy's automatic HTTPS and HTTP redirect. Publish A records and AAAA records only for working IPv6. Permit inbound TCP 22, 80 and 443 in both the host and provider firewalls, and restrict SSH by source where practical. Before closing the initial SSH connection, verify named-user key login, sudo and console recovery in a second session. Disable root SSH and password and keyboard-interactive SSH login. Enable Fail2ban for SSH and automatic security updates with a reviewed reboot window. Check the PostgreSQL update source and verify patches are applied for that source. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) · [Ubuntu security updates](https://documentation.ubuntu.com/security/security-updates/)
- **Proxy and clock.** Keep the app's nonce CSP, HSTS, secure host-only cookies and private cache controls. Set `APP_ORIGIN` to the exact public HTTPS origin with no trailing slash. Enable `TRUST_PROXY=true` only after confirming Caddy replaces spoofed forwarding headers and Next cannot be reached directly. Avoid a CDN or another proxy at launch. Set the host, PostgreSQL and operator timestamps to UTC, keep app business dates in Asia/Manila, and schedule jobs in Manila time. Use chrony or the distro's supported NTP service as the sole synchronizer. Check sync, offsets and alerts before accepting time, MFA or payroll. Validate TLS, upload limits and streaming through the proxy. [Caddy reverse proxy header behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

## 2. Secrets and keys

Generate independent runtime, auth and migration database passwords, a cryptographically random `SESSION_SECRET`, a 32-byte MFA key with a unique key ID, and a 32-byte upload capability key encoded as 64 hex characters. Generate on the server with a restrictive umask and write to protected files or credential storage. The web service receives the two app database URLs, origin, session secret, MFA keyring, upload capability and storage path. Migration, backup and operator credentials use separate files or systemd credentials. Provision secrets without shell history, arguments, command tracing, echoed prompts, committed dotenv files or journal entries. The database stores only the upload capability's SHA-256 verifier.

Back up the encrypted MFA keyring **separately from the database and private-file archives**, with separate access controls. Retain the key IDs and old keys needed to restore retained backups. Document adding a new ID, restarting with both keys, running the audited re-encryption tool and retiring old keys only after the retention window permits. If the entire keyring is lost, enrolled users must re-enroll through recovery or verified reset. The database cannot recover those keys. Keep the encrypted runtime configuration and archive decryption recovery instructions separately as well. For upload key loss or rotation, stop writers, rebind the verifier and update the runtime secret together, then check pending and available files. [Existing MFA recovery and rotation notes](../README.md#mfa-keyring-backup-loss-and-rotation)

## 3. First run and administrator onboarding

1. Provision the cluster, roles, storage and secrets. Obtain the exact approved revision and use `pnpm install --frozen-lockfile` and `pnpm build` as an unprivileged build user. Use a separate operator environment for `pnpm db:migrate`. Verify migration status, ownership, grants and 43 RLS-enabled application tables before creating accounts.
2. Use an audited, server-only bootstrap operation to create the named first administrator, baseline SECURITY and WORK policies, empty PAY policy, company settings and the upload key verifier in one transaction. Require the expected environment and database, migration ownership, an empty target and explicit `--allow-production`. Give the administrator an individually generated temporary password through a private password-manager channel. Force password change and real-phone TOTP confirmation before access. Record the action and outcome without recording the password, TOTP or recovery codes.
3. Use an explicit audited operator action to create a different named second administrator with independent credentials, password change, TOTP and individually stored recovery codes. Verify that each can sign in independently and that either can assist the other. Existing production-mode seed guards stay in force. Exclude development seeds, QA fixtures and test secrets from the production release and operator instructions.
4. Start systemd and Caddy in a restricted smoke-test window. Confirm TLS and redirect, origin and cookie rules, two MFA admin sign-ins, empty initial PAY state and zero demo users. Check auth and application connectivity, service restart, time synchronization and private-path permissions. Run destructive security, upload and payroll smoke cases against staging fake accounts. Verify that recovery and cleanup operator commands refuse the production target without their explicit flag. Record smoke results and promote access only at the go-live gate.

## 4. Backup and restore

- **Capture.** Nightly, within the configured window, wait for open shifts to clear. If the wait expires, skip and alert while leaving the app running. A final shared table lock and recheck block a racing Clock In while maintenance begins and the app stops. Serialize all other writers including reconciliation, deployment and cleanup. Verify writer quiescence, then take a custom-format `pg_dump` and archive the entire matching private root. Include work objects, quarantine and payslip directories. Resume the app once both parts of the local capture are complete. Encrypt and transfer the bundle offsite, verify delivery and remove local plaintext scratch data. [PostgreSQL backup behavior and role scope](https://www.postgresql.org/docs/18/app-pgdump.html)
- **Bundle and destination.** Record a common backup ID, UTC timestamp, app revision, PostgreSQL and migration versions, role provisioning reference, file checksums and key IDs. Keep secrets and password verifiers out of the manifest. Use client-side authenticated encryption with the recovery key held outside the VPS and a separate offsite account with MFA. Proposed destinations are a private AWS S3 or Backblaze B2 bucket with immutable retention, or a separate managed SSH backup host. Scope the VPS credential to write the required backup objects. Use a separate recovery identity for retrieval and a separate policy for retention. Confirm storage region and vendor access with the owner. [AWS S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html) · [Backblaze B2 Object Lock](https://help.backblaze.com/hc/en-us/articles/360052973274-Object-Lock-FAQs)
- **Retention and objectives.** Propose 14 daily, 8 weekly and 6 monthly restore points, plus a verified pre-migration backup retained through its rollback window. Target no more than 24 hours of data loss after a successful nightly backup and a four-hour restore. Measure the actual recovery time and alert on missing or stale offsite backups. These are operating targets for owner approval.
- **Rehearsal.** The owner restores one offsite bundle to an isolated scratch server or PostgreSQL cluster with a separate private root and restricted network access. Provision the role names with fresh passwords, restore schema, data, ownership and ACLs, then restore the matching file bytes and verify manifest, hashes and filesystem permissions. Load the matching separately held keyring, rebind a fresh upload capability if needed, and invalidate restored sessions, duty reauthentication handles, unfinished challenges and reset tokens before any access. Verify migration status, 43 RLS tables and grants, clock sync, fresh MFA sign-in, attendance and payroll history, authorized downloads and peer denial. Record backup ID, timings, results, deviations and scratch disposal. Use synthetic staging data for the first drill and verify the initial production backup separately before opening staff access. **No go-live until one complete offsite restore rehearsal passes.** Repeat quarterly and after material changes to storage or recovery.

## 5. Scheduled maintenance and alerts

| Schedule in Asia/Manila | Operation and evidence |
| --- | --- |
| Daily at 01:30 | Run the existing attendance reconciliation via an operator-only systemd oneshot and persistent timer. Confirm it uses the configured batch limit, report counts, and alert for error or remaining backlog. Use bounded repeat batches or an operator follow-up when needed. |
| Nightly at 02:30 | Capture and deliver the encrypted database and private-file pair. Use a shared operations lock so it cannot overlap reconciliation, cleanup or deploy. Check successful offsite delivery with an external heartbeat. Confirm the window suits overnight staff. |
| Weekly review | Inspect aged failed uploads and payslip orphans. Run the existing cleanup CLIs only against the verified environment with explicit production authorization. Review audit and retained published files. |
| Daily and weekly checks | Confirm automatic package security updates and job health. Review disk, backup growth, journal retention, PostgreSQL maintenance and pending reboots. Schedule restarts in a maintenance window. |

Timers run with explicit target, working directory and credentials. The existing guarded operator commands receive `--allow-production` only from dedicated, documented invocations that identify the intended database. A systemd failure hook and external dead-man check alert the owner through an agreed channel using only host, job, time and result. Logs record counts and exit status. No passwords, MFA tokens, payroll contents or backup credentials enter logs.

## 6. Staging, deployment and rollback

- **Staging.** Use a second hostname such as `team-staging.example.com` on the same VPS, restricted at Caddy to approved test networks. Give it an independent PostgreSQL cluster, ports, service user, private storage, credentials, keyring and HTTPS origin. Run the production build in production mode. Create synthetic people through the release bootstrap and ordinary workflows. Use a separate disposable local QA environment for fixture scripts. Keep production employee data out of staging.
- **Deploy.** Record the target commit and prior release. Fetch and verify the exact commit or archive, install from the frozen lockfile, build in a new directory and rehearse migration and rollback on staging first. For production, acquire the operations lock, put the app in maintenance and stop writers. Take and verify a paired offsite backup from that quiesced state and keep writers stopped through migration. Apply `prisma migrate deploy` with migration authority. Verify schema and grants, switch `current`, restart and smoke test before reopening. Keep the previous release and record operator, times, migration status and results. Keep production migration credentials outside systemd's app unit.
- **Rollback.** If the schema is unchanged or the prior build was verified against the new schema, return the symlink to the prior release and smoke test. For incompatible schema or data changes, keep maintenance enabled, capture the failed state for investigation and restore the matched pre-deploy database and files to clean targets with compatible secrets. Invalidate restored auth artifacts and verify before switching back. If users have written since cutover, quantify and preserve those writes for owner reconciliation before any restore that would lose them. Resolve migration failures using the documented Prisma recovery procedure after inspecting the database. Never improvise a down migration or use `prisma db push`.

## 7. Monitoring and account operations

Configure an external HTTPS uptime and certificate check on the login page without credentials. Add alerts for repeated failures, backup age, time-sync loss or material drift, persistent low available memory or OOM, disk usage and inodes. Start with disk warning at 75% and urgent at 85%, then adjust from staging evidence. Use systemd journal for app and job units, Caddy access and error logs with sensitive fields excluded, and PostgreSQL service logs. Set bounded retention and rotation, restrict log readers, and give the owner commands to inspect service status, job failures, auth and audit events. Pair the public login probe with a periodic operator check of authenticated database connectivity.

Document session scope and expiry, logout, account disable, duty revoke, lockout expiry and the security and audit views. Use the existing reset procedures with identity verification for lost phones. A user with their password and a recovery code can enroll a new authenticator. When the phone and recovery codes are unavailable, use the second administrator's audited assistance. A lost password follows the separate verified password-reset flow when an eligible administrator is available. For the last administrator who still knows their password, use the existing migration-owner MFA reset CLI with explicit production flag and interactive confirmation. If the last administrator also loses the password, suspend access and escalate to the owner for a separately authorized recovery decision. Test recovery while the second account is available and keep each administrator's recovery codes separately.

## 8. Security and Philippine employee-data review

- **Database and filesystem.** Check live owners, flags, role memberships, ACLs, definer function grants and all 43 RLS tables after migration. Exercise scoped employee A/B reads in staging with the actual runtime role. In production verify anonymous/default-deny behavior and the restricted-role grant probes without adding fake employees. Check that runtime cannot read credential material, auth cannot read payroll, neither role can assume owner authority, and finalized financial and audit data are protected. Verify file roots, symlink restrictions and no direct web path to protected content.
- **Owner-run security checklist.** Check public listening ports, HTTPS renewal, HSTS, production CSP and cookie flags. Test spoofed forwarding headers, invalid CSRF origin, disabled sessions, unauthenticated and foreign guessed IDs, revoked streams, and malformed or oversized uploads. Check attachment disposition, no-store, blocked HEAD and Range, and the approved/paid distinction. Existing streamed payroll pages can carry a not-found result inside HTTP 200. Confirm no foreign payload and consistent HTTP 404 from the protected APIs. Run dependency audit against the release lockfile and triage findings before launch.
- **Data inventory and access.** Document account identifiers and contacts, employment metadata, schedules and rates, duty and attendance records, task contributions, submissions and files, payroll amounts and adjustments, payment dates and references, payslips, auth and audit history, and protected hashes or encrypted MFA data. Employees access their own profile, attendance and payroll and their authorized work. MFA administrators manage workforce records and payroll. System and backup operators have restricted infrastructure access. The owner approves access for accounting staff, payroll exports and any service providers.
- **Retention and deletion.** Have the owner and Philippine privacy/legal adviser approve the privacy notice, access review, retention periods by data class, incident response and applicable reporting obligations. Deactivate departing accounts and revoke access. Preserve required approved time, financial and audit history, including under a legal hold. Delete or anonymize eligible records and files through a reviewed process with evidence and corresponding backup expiry. Review safeguards for provider location, exports, staff requests and incidents. This is an operating proposal for legal and owner review, not legal advice. [Philippine Data Privacy Act](https://privacy.gov.ph/data-privacy-act/) · [National Privacy Commission breach reporting](https://privacy.gov.ph/pips-and-pics/breach-reporting/)
